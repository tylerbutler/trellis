## What works

## Priority issues

### 1. [P2] Group the docs navigation by reader intent

The sidebar presents 11 peer destinations, from Installation through JSON output and Compatibility (`website/astro.config.mjs:19-33`). A new evaluator must understand the product's divisions before choosing a route.

**Fix:** Introduce a few meaningful groups, such as Start, Workspace tasks, Releases, and Reference. Keep direct access to every page. **Command:** `/impeccable shape`.

### 2. [P2] Bring the proof forward and identify its source

"Opinionated, but modular" appears before "The glue this replaces" (`website/src/pages/index.astro:72-120`). The strongest argument arrives after visitors have processed the adoption layers. The ledger and "Real output" caption also omit provenance.

**Fix:** Put the concrete glue example immediately after the hero. Name and link the lattice case study where it supports a claim, and distinguish measured examples from illustrative output. Keep the modular-adoption explanation as reassurance after the proof. **Command:** `/impeccable clarify`.

### 3. [P2] Add a quick-entry layer to the large reference pages

Configuration combines setup, key reference, exclusions, release behavior, templates, migration, and validation. The CLI reference contains 29 command sections. Their completeness is valuable; the problem is finding the relevant part quickly.

**Fix:** Add a compact, task-grouped index at the top of each page. Keep the exhaustive material underneath. Change the generated CLI reference through its generator, not by hand. **Commands:** `/impeccable distill`, then `/impeccable layout`.

### 4. [P2] Increase mobile control hit areas

Measured deployed targets include a 32×32 menu button, a 34×40 search button, and 404 links about 33px high. These work, but are less comfortable to tap than 44×44 targets. This alone is not a WCAG 2.1 AA failure.

**Fix:** Increase hit areas without enlarging the icons or changing the visual language (`website/src/styles/starlight.css:120-123,166-178`). **Command:** `/impeccable adapt`.

## Cognitive load and emotional journey

**Moderate load:** three checklist concerns — chunking, choice grouping, and progressive disclosure. The flat sidebar and large configuration page create the main burden. Complex domain material does not need to be removed; it needs a clearer entry path.

The hero establishes confidence quickly. The adoption-layer section then creates a brief information valley before the ledger, configuration, and `doctor` output supply the strongest proof. Installation ends well with verification and a low-commitment next step.

## Persona red flags

- **First-time Gleam maintainer:** Understands the positioning quickly, but must learn the adoption layers before seeing the concrete replacement case.
- **Power reader:** Has search and anchors, but no compact command taxonomy for scanning the 29-section reference.
- **Mobile reader:** Gets readable content and no page overflow, but several persistent controls have small touch areas.
