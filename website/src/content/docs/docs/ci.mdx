Trellis runs identically locally and in CI, and emits the exact structures
GitHub Actions consumes, so workspace workflows shrink to thin triggers around
a few commands. The recipes below are the shapes a Gleam workspace actually
needs.

## Installing trellis

The shell installer puts a prebuilt binary on the runner in about a second.
Pin the version so CI doesn't move under you (see
[installation](/docs/installation/) for other options, including a
`.tool-versions` pin through mise/asdf):

<Code
  lang="yaml"
  code={`- name: Install trellis
  run: |

      https://github.com/tylerbutler/trellis/releases/download/v${TRELLIS_VERSION}/trellis-gleam-installer.sh | sh
    # the installer adds its install dir to $GITHUB_PATH automatically`}

## An affected-only test matrix

`trellis ci matrix` emits a strategy matrix
(`{"include":[{"name","path","version"},…]}`). With `--since` it covers only
the packages a PR touched, dependents included:

```yaml title=".github/workflows/ci.yml"
jobs:
  plan:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.plan.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # --since needs history
      - id: plan
        run: echo "matrix=$(trellis ci matrix --since origin/main)" >> "$GITHUB_OUTPUT"

  test:
    needs: plan
    runs-on: ubuntu-latest
    strategy:
      matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}
    steps:
      - uses: actions/checkout@v4
      - run: trellis run test ${{ matrix.name }} --target all
```

<Callout>

Full fan-out is the default. `--since` is opt-in because coupling the path-dep
graph can't see would otherwise go silently untested, so a workspace that wants
affected-only CI writes `--since origin/main` into its workflow explicitly.

</Callout>

## Workspace facts as outputs

`trellis ci outputs` emits workspace facts as `key=value` lines, ready for
`$GITHUB_OUTPUT`:

```console
$ trellis ci outputs
packages=["lat_core","lat_mid","lat_cli","lat_example"]
releasable=["lat_core","lat_mid","lat_cli"]
version_files=["packages/lat_core/gleam.toml","packages/lat_mid/gleam.toml","packages/lat_cli/gleam.toml"]
tags=["lat_core-v1.2.0","lat_mid-v0.5.1","lat_cli-v0.4.3"]
series_tags=["lat_cli-v0.4"]
```

`tags` lists the immutable per-version tags and `series_tags` the moving ones,
each covering only the packages whose
[`package_tags`](/docs/configuration-reference/#tags) includes that level — so a
workspace with no `exact` entry reports an empty `tags`. Repository tags are
deliberately absent from both outputs because they do not identify packages.

Both `ci matrix` and `ci outputs` are shaped by GitHub rather than by trellis,
which is why neither carries the `schema` field every other payload does — see
[JSON output](/docs/json-output/) for what each one promises.

## PR gates

Run `doctor` on every PR — it checks every workspace invariant at once and
exits non-zero on any error. Pair it with `changelog check`, which fails a PR
that changes a package without logging it:

```yaml
# on: pull_request
- run: trellis doctor
- run: trellis changelog check --base "origin/${{ github.base_ref }}"
```

A workspace with [pinned git dependencies](/docs/pinning/) can add `trellis pin --check`, which fails the PR when a pinned SHA is no longer reachable from its tracked ref. `doctor` reports the same drift, but only as a warning.

When the tripwire fires on a mechanical finding, such as a missing
`CHANGELOG.md` or a stale `manifest.toml` locked version, clear it locally with
`trellis doctor --fix`, which applies exactly those fixes and re-reports the
rest. `--fix` never touches the report-only findings (path-dep escapes, tag
collisions, versions behind their changelog), so it stays safe to run
anywhere; keep the bare `trellis doctor` in CI as the gate.

### The changelog comment

A failing gate in a log is easy to miss. `changelog check --format github`
emits `key=value` lines for `$GITHUB_OUTPUT`, so the same run that gates the
PR also drives a sticky comment, with no `jq` and no second tool:

```yaml
# on: pull_request
permissions:
  pull-requests: write

steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0 # the diff needs the base commit
  - id: changelog
    # The gate exits 1 on a missing entry. Let it, but keep going, so the
    # comment lands before the job fails.
    continue-on-error: true
    run: |
      trellis changelog check \
        --base "${{ github.event.pull_request.base.sha }}" \
        --head "${{ github.event.pull_request.head.sha }}" \
        --format github >> "$GITHUB_OUTPUT"
  - name: Post the changelog comment
    if: >-
      steps.changelog.outputs.has_entries == 'true'
      || steps.changelog.outputs.needs_entry == 'true'
      || steps.changelog.outputs.invalid_fragments != '[]'
    uses: marocchino/sticky-pull-request-comment@v3
    with:
      header: changelog
      message: ${{ steps.changelog.outputs.preview }}
  - name: Remove it when there is nothing to say
    if: >-
      steps.changelog.outputs.has_entries == 'false'
      && steps.changelog.outputs.needs_entry == 'false'
      && steps.changelog.outputs.invalid_fragments == '[]'
    uses: marocchino/sticky-pull-request-comment@v3
    with:
      header: changelog
      delete: true
  - name: Fail if the check did
    if: steps.changelog.outputs.ok != 'true'
    run: exit 1
```

The comment appears when there is something to say (entries to preview, an
entry missing, or a fragment that doesn't parse) and is deleted when there
isn't, so a fixed PR doesn't keep a stale complaint. It shows each changed
package's fragment count and planned next version, plus a collapsible release
preview of the changelog sections this PR's own fragments would produce,
ripple bumps included. Everything it counts is [scoped to the
branch](/docs/changelog/#scope): fragments already unreleased on the base
branch answer for the PRs that added them, not this one. `ok` carries the
verdict `continue-on-error` swallowed, and is empty if trellis could not run
at all, which fails the job either way.

`preview` is already the comment body, rendered from the same data as the
`--format json` field of that name. `needs_entry_packages` and
`invalid_fragments` are JSON arrays if you would rather compose your own:

```yaml
- run: echo "Missing: ${{ join(fromJSON(steps.changelog.outputs.needs_entry_packages), ', ') }}"
```

A workspace that wants the comment without the gate sets
[`changelog.strictness`](/docs/configuration-reference/#keys) to `warn`, which makes
`ok` true even when `needs_entry` is — then drop both the
`continue-on-error` line and the final step.

### Annotating the diff

A `doctor` failure in a log tells a contributor a file is wrong; an annotation puts the message on the file itself in the PR's Files tab. `--format github` emits one workflow command per finding and nothing else, so it drops straight into the gate:

```yaml
# on: pull_request
- run: trellis doctor --format github
```

Errors become `::error`, advisory warnings become `::warning`, and the exit
code is unchanged, so the job still fails on any error. A healthy workspace
prints nothing at all.

For anything richer than annotations, such as grouping findings by package,
rendering them into a sticky comment, or filtering to the ones `--fix` would
clear, use `--format json` and read `check`, `severity`, `file`, and `fixable`
off each finding:

```yaml
- id: doctor
  run: trellis doctor --format json > doctor.json || true
- run: jq -r '.findings[] | select(.fixable) | .message' doctor.json
```

The [payload is stable](/docs/json-output/); the `message` prose is not.

It is an example for packages on Hex, not trellis's own Cargo release pipeline.

### Setup

- Install trellis using the [reviewed source snapshot](#installing-the-fixed-trellis)
  below. No currently published release, including v1.1.0, supports these
  release PR options. After the fixes ship, you can instead set the repository
  variable `TRELLIS_VERSION` to that release's exact version; do not use
  `latest`. The example also pins Gleam and Erlang/OTP; change those pins to
  versions supported by your packages.
- Install a GitHub App on the workspace repository with **Contents**,
  **Pull requests**, and **Commit statuses** read/write permissions. Store its
  ID and private key as `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY`.
  Preparation uses the App token so its branch push and PR creation trigger
  ordinary validation workflows; the default Actions token does not.
- Store a Hex API key that can publish the workspace's packages as
  `HEXPM_API_KEY`. The workflow exposes it only to the merge publication step.
  The workflow token needs `contents: write`, `pull-requests: read`, and
  `statuses: write` for tags, releases, merge checks, and publication status.
- Protect `main` with your normal required checks and reviews, including for
  `release/pending`. Restrict who can push that release branch and dispatch
  releases. Treat a merge from that same-repository branch as permission to
  publish; a matching branch name on a fork is not trusted.
- Keep `main` and `release/pending` as shown, or change **all** branch checks,
  triggers, and command arguments together. Do not add a separate tag-triggered
  publishing workflow for this flow.

### Installing the fixed trellis

The example works before a fixed binary release is published. Leave
`TRELLIS_VERSION` unset and check a **reviewed fixed source snapshot** into
your Gleam repository at `.github/trellis`. From the consuming repository's
root, copy from the checkout containing these fixes:

```sh
TRELLIS_SOURCE=/path/to/reviewed/fixed/trellis-checkout
mkdir -p .github/trellis
cp "$TRELLIS_SOURCE/Cargo.toml" "$TRELLIS_SOURCE/Cargo.lock" \
  "$TRELLIS_SOURCE/build.rs" "$TRELLIS_SOURCE/LICENSE" .github/trellis/
cp -R "$TRELLIS_SOURCE/src" .github/trellis/
```

Record the reviewed source revision with your adoption change, and keep the
snapshot and lockfile together. The install target embeds no external assets:
the website file embedded in `src/main.rs` is inside `#[cfg(test)]` and is not
compiled by `cargo install`. There is no need to copy the website, generated
man pages, tests, or build output. If you update the snapshot, check its
`include_str!`/`include_bytes!` paths and copy any newly required build assets
at the same relative paths.

The workflow checks out the approved merge for publication, or current `main`
for preparation, before installing. It builds the checked-in snapshot with
Rust 1.94.1 and `cargo install --locked`. Both `CARGO_TARGET_DIR` and the
installation root are under `RUNNER_TEMP`, not the source tree, so build
artifacts cannot break `release pr`'s clean-tree check. Source installation
fails if the snapshot is absent or cannot compile; it never silently falls
back to an older binary.

Once a release containing these fixes is published, set `TRELLIS_VERSION` to
that exact version to use its prebuilt installer instead. Until then, setting
it to v1.1.0 or an older published release does not supply the required CLI.

### Adopting existing releases

If the repository already has merged release PRs from `release/pending`, the
latest one must have a successful `trellis/release` commit status before the
example prepares another release. During adoption, verify that **every**
package at that PR's merge commit is published as required, and that its tags
and GitHub releases are complete. Only then record success on that exact commit:

```sh
# Set RELEASE_SHA to the verified historical release PR's merge commit.
gh api --method POST "repos/OWNER/REPO/statuses/$RELEASE_SHA" \
  -f context=trellis/release -f state=success \
  -f description='Historical publication and tagging verified'
```

Never mark an unknown or partial release successful. Recover it at its approved
merge commit first, not at current `main`. With no historical matching release
PR, there is no adoption status to seed.

### Dispatch and ownership

Select **main** in the Actions **Run workflow** menu. For the first candidate,
enter `rc` in `pre` and targets such as `lat_core=1.3.0` in `set`, one per line.
Use `bump` for repeatable `package=major|minor|patch` overrides instead.
The inputs are passed as argument arrays; they are not shell commands.
After that candidate merges and publication succeeds, dispatch `pre: rc`
again for the next candidate, or `pre: none` for stable promotion. See the
[candidate lifecycle](/docs/publishing/#candidates-and-promotion).

All preparation and publication runs share `trellis-release` concurrency with
`queue: max` and no in-progress cancellation. GitHub permits up to 100 pending
runs; further runs are canceled. Queue order follows when runs begin waiting,
not dispatch order. Dispatch the next candidate only after the previous one
has merged and published; a queue is not a sequence of version requests.
External callers of `release pr` must follow the same ownership policy.

Automatic pushes refresh ordinary stable release PRs. They pause when a pending
PR contains a prerelease, when releasable manifests on `main` contain
prereleases, or when a manual request owns preparation. Manual requests write a
durable `trellis/release_request` pending status on their base commit **before**
running `release pr`. That reservation protects even a stable promotion PR and
the failure window before a PR exists; later unrelated pushes do not erase it.
It stays in force until a subsequent release PR merges, or a successful manual
no-op clears it. Fix a failed manual request and rerun or dispatch it again.
To abandon it, close its pending PR and explicitly clear its reservation status
on the recorded base commit; do not silently hand an unfinished request to
automatic preparation.

The ownership check scans commit statuses back through the latest merged
release. Before the first matching release PR, it scans main's full history;
large repositories can hit GitHub's API rate limit. Such an API failure stops
preparation rather than bypassing ownership. In a large repository with no
matching release PR, dispatch the first stable release manually with empty
inputs. Once that PR merges and publishes, later automatic scans stop at its
merge commit.

### Publication and recovery

Only a merged `release/pending` PR targeting `main` from the same repository
publishes. The workflow checks out its immutable `merge_commit_sha`, writes
`trellis/release: pending`, and runs:

```sh
trellis publish --all-untagged
trellis tag create --push --github-release
```

Success means **both** commands completed. Failure leaves a failed or pending
status, never a successful fallback. Before preparing another release, the
workflow finds the most recently merged release PR and requires that commit's
`trellis/release` status to be `success`. Missing status also blocks, including
the window before the merge-triggered run starts.

Recover by rerunning the failed **merge-event** workflow, not by dispatching a
new version. Its checkout remains the same approved merge commit even if
`main` has advanced. Hex checks skip already-published versions; tagging
reconciles existing remote tags and skips existing GitHub releases. Completed
old publication runs skip publication and tagging, so they cannot move series
tags backward. They still retry gated preparation from **current** `main`;
rerunning also recovers an App-token, checkout, or preparation failure that
happened after publication succeeded.

After successful publication, the same serialized run checks out **current**
`main` and rechecks the preparation gates. A candidate keeps automatic
preparation paused. A published stable promotion restores it immediately,
without needing an unrelated push.

The [tags-as-trigger alternative](/docs/publishing/#two-release-shapes) remains
supported for stable-only pipelines. It needs immutable exact package tags;
`publish --tag` rejects moving series tags.
